# laconic v0.1.0 — known limits and deferred findings

What the review process decided *not* to fix, and why. Written at tag `laconic--v0.1.0`
so the next person does not have to re-derive it.

## Eval results, and what they do and do not show

**Addressed, partially, by [`evals/results/2026-07-31-benchmark.md`](../evals/results/2026-07-31-benchmark.md)**
(320-generation, n=5, two-model run; snapshot committed at `evals/snapshots/`, generated
against commit `2b1e3ce`). The single-sample framing below described the v0.1.0-era
`evals/run.sh` output only; it is superseded, not deleted, because it is still the
correct description of what `evals/run.sh` itself produces today.

That document has since been corrected: it retracts a trap-pass-rate claim this section
originally leaned on (contamination and circularity in the case design — see its
"Trap-based claims: retracted" section), corrects a false readability claim, and discloses
that the plugin currently fails its own gate in 4 cells. "Resolved" was too strong for what
that run actually supports; see the correction below for `decision` specifically.

Run at level `full`, one sample per case, on the cheapest model, with the rules delivered
via `claude -p --append-system-prompt` rather than the hook path a real session uses.
Enough to say a trap fired; not enough to conclude a rule needs rewriting.

| Case | Result |
| --- | --- |
| `walkthrough` | PASS. The requested explanation kept its detail, including both branches the prompt named. |
| `destructive` | Warning survived compression intact and uncut — the `invoices` FK that blocks the drop and the `sessions` cascade both named, in complete sentences. Dropped the fixture's row count, which `CRITERIA.md` now grades as a soft note rather than a hard fail. |
| `badnews` | Bad news stated plainly. Terseness failed: the terse arm was longer than the control and added a closing offer. That pointed at a real gap in the rule text, now fixed — see below. |

## Deferred, with reasoning

**`decision`'s unrequested alternative — not a rule defect.** The control arm did the same
thing, so the rules did not introduce the behavior, and the rule text ("No unrequested
alternatives, no 'you could also'") is unambiguous. At one sample on the cheapest model
this cannot be distinguished from an adherence ceiling. Re-run at higher n on a stronger
model before touching `rules/laconic.md`.

**`badnews`'s closing offer — this one *was* a rule defect, and it is fixed.** Worth
recording because the reasoning generalizes: the rule listed only pleasantries ("Let me
know if...", "Hope this helps") as examples, so an offer to do more work ("Want me to...?")
fell outside the category the examples defined. That is a textual observation, not a
statistical one — a two-example list cannot define a three-form category — so it needed no
additional eval samples. The category now covers work-offers, with a carve-out that asking
permission before a destructive action is never a closing offer.

**Both deferrals re-examined at n=5, two models —
[`evals/results/2026-07-31-benchmark.md`](../evals/results/2026-07-31-benchmark.md).**
This is the higher-n, stronger-model re-run both deferrals above were waiting on.

- `decision`'s unrequested alternative — the 8/10 pass count cited in an earlier version
  of this note is **not valid evidence, and is withdrawn.** `decision` is one of the two
  cases (with `floor`) whose judge criteria are lifted verbatim from `rules/laconic.md`'s
  own prohibitions ("surveys both options," "closes with an offer"), so a trap-pass-rate
  comparison on this case scores the treatment against its own instructions — see
  "Trap-based claims: still retracted" in
  [`evals/results/2026-07-31-benchmark.md`](../evals/results/2026-07-31-benchmark.md) for
  the full contamination and circularity finding. No trap-based claim is made from this
  case, in either direction.

  **The deferral this left open is now closed** (issue #9). Three cases — `fail-open`,
  `silent-success`, `stale-cache` — were written from a fixture rather than from the rule
  text, and generated across all four arms together. Laconic answered 27 of 30 correctly
  against baseline's 28 of 30, so the answer-quality question `decision` could not settle
  has been settled at a coarse resolution: **no quality regression, down to a detection
  floor of about a 30-point drop.** `decision` itself was not redesigned and remains
  contaminated; it is now marked `grading: rule-adherence` in its `expect.json`, and
  `tests/test_evals_layout.sh` fails if anyone relabels it `quality` without rewriting the
  criteria. See "Answer quality" in the results document.
- `badnews`'s closing-offer fix **held.** Laconic passed `badnews` 10/10, matching every
  other arm (also 10/10) — but `badnews` is one of the cases that scored 10/10 for every
  arm in this run, so it currently provides no discriminating signal beyond "the fixed
  rule text did not regress." Treat as confirmed-not-broken rather than strongly
  validated. This one is a plain pass-count reading, not a trap-based claim in the sense
  retracted above — `badnews`'s grading criteria are not drawn from `rules/laconic.md`'s
  own text, though the requirement that bad news be reported at all is, which is why it is
  now classified `grading: safety` rather than `quality`.

**The `destructive` blast-radius punt — a third defect of the same textual kind, fixed
(issue #3).** The never-cut bullet said "including exactly what will be affected", which
does not say *from the material in front of you*, so a response that listed the generic
foreign-key checks and offered to go read the schema itself read as compliant. The
benchmark caught one: `destructive/haiku` rep2, recorded with `num_turns: 1`, which never
opened the fixture at all. Same shape as the closing-offer gap above — a requirement whose
wording did not cover one of its forms — and fixed the same way, by tightening the
sentence rather than adding a bullet. Re-run clean at n=5 on both models;
[`evals/results/2026-07-31-destructive-recheck.md`](../evals/results/2026-07-31-destructive-recheck.md)
carries the argument, the numbers, and the failure mode on haiku this did *not* fix.

**Switch detection greps the raw payload instead of parsing JSON.** A malformed payload
containing an unescaped `"prompt": "/laconic off"` inside the prompt text could match. Not
reachable through normal JSON encoding, since a literal `"` inside a string value must be
escaped, and accepted as the cost of the no-`jq` constraint.

**No native-Windows PowerShell port** — RESOLVED (issue #2). It was dropped in v0.1.0 because
neither `pwsh` nor `powershell` was available to verify one against, and an unverified script
that writes into model context is worse than none. `windows-latest` CI removed that
constraint, which is trigger 2 in
[`windows-support-spec.md`](windows-support-spec.md). `hooks/laconic.ps1` and
`hooks/laconic-statusline.ps1` now ship alongside the bash scripts, `hooks.json` selects
between them per platform, and `tests/test_laconic.ps1` runs the same numbered cases on
`windows-latest` — including the cross-platform case a per-platform suite would miss, that a
flag file written by either implementation is accepted by the other.

Note that switch detection on the PowerShell side uses `ConvertFrom-Json`, so the
raw-payload limit recorded above does not apply to it. The bash grep stays as it is: the
two implementations agree on every reachable input, and diverge only on a malformed payload
that normal JSON encoding cannot produce.

**`evals/results/` is gitignored** — RESOLVED by the 2026-07-30 benchmark run. `.gitignore`
now excludes only `evals/scratch/` (the ad hoc `evals/run.sh` output); `evals/results/`
and the snapshots it is generated from (`evals/snapshots/results.json`,
`evals/snapshots/judgments.json`) are committed and diffable. Any future change to a
published number is now reviewable as a diff, which is what this caveat asked for.

**`tests/test_rules.sh` reads the rules file's last line via `wc -l`**, which would drop
the final line if the file ever lost its trailing newline. Safe today; it would only mask
an ultra-sentinel failure.

## Reserved for a human

- **Publishing.** No `origin` remote exists and nothing has been pushed. The README's
  marketplace install block is marked "once published" until that happens.
- **The interactive end-to-end check.** Verified mechanically — `remind` mode with a
  `/laconic full` payload, then `/laconic off` — but not in a live session. The exact steps
  are in the README's Development section: run `/laconic full`, confirm responses get
  terser, run `/laconic off`, confirm the reminder line stops.
