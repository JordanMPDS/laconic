# The subagent path — 2026-07-31

[Issue #6](https://github.com/JordanMPDS/laconic/issues/6) asks whether `SubagentStart`
should keep injecting the rules. Its own summary of the evidence was "nothing": no eval
covered the subagent path, and the current behaviour was asserted rather than measured.
This is option 3, measure first.

**Result: no measurable degradation, at any level.** A parent model answering from a
laconic subagent's report is as accurate as one answering from an unrestricted subagent's
report — 91% against 91% on the arm-fair cases, with every arm-versus-baseline comparison
at p = 1.000. The reports themselves are 41–46% shorter on sonnet. Never-cut tokens
survived the handoff in all 120 relayed answers that carry them, 30 in each arm.

What this rules out is the specific harm the issue names — that laconic "may cut exactly
the context the parent needs to act correctly." On these eleven cases, at n = 264, it does
not. The section [What this cannot answer](#what-this-cannot-answer) lists what remains
open.

**Decision taken on this evidence: option 1, drop the hook.** `SubagentStart` is gone from
`hooks/hooks.json` and `subagent` is no longer a mode of `laconic.sh` or `laconic.ps1`. The
reasoning is not that the rules hurt — they measurably do not — but that they were not
buying anything. laconic exists to make a response pleasant and cheap for a *person* to
read, and a subagent's report has no such reader. On that path the only two currencies are
accuracy, which this run found flat in every arm, and tokens, which
[How good was the compression](#how-good-was-the-compression-and-what-it-cost) found move
the wrong way: 6-16% more per subagent call. A cost with no measurable benefit is worth
removing even when it is also harmless.

Note what this decision does **not** rest on: laconic's value in a normal session is
readability, which no eval here or elsewhere in `evals/` has ever measured. That question
is open and tracked separately; nothing above should be read as evidence about the
`SessionStart` path.

## What was measured

A relay, in two stages.

Stage one already existed. Every response in the committed snapshots was produced by a
model that read a fixture with tools and wrote up what it found, which is structurally
what a subagent hands back to its parent. Four of those response sets are used as the
four arms:

| arm | reports come from | what it stands for |
| --- | --- | --- |
| `via-baseline` | `results.json`, `baseline` arm | issue option 1 — drop the hook |
| `via-lite` | `levels-lite.json` | issue option 2 — pin subagents to `lite` |
| `via-full` | `levels-full.json` | what ships today |
| `via-ultra` | `levels-ultra.json` | the sharpest form of the worry |

Stage two is new. Each report, and nothing else, is handed to a parent model in an empty
directory, which is asked to answer the original task. The parent's answer is then graded
by the same blind judge, against the same `expect.json`, that grades a direct answer.

The relay prompt is byte-identical in every arm, never names the arm or the plugin, and is
asserted to be so by `tests/test_bench.py`. The parent is told it cannot see the files,
because otherwise it spends its turn looking for them and answers "I need the repository"
in every arm alike — which would measure the harness rather than the handoff.

## What is fair to compare, and what is not

`evals/CRITERIA.md` splits the cases by where their trap criteria came from, and that
split still governs here, with one change in the reasoning.

- **`quality`** (`fail-open`, `silent-success`, `stale-cache`) — criteria from the fixture
  alone. A pass means the parent's answer was *right*. Fully comparable.
- **`safety`** (`badnews`, `code-fidelity`, `destructive`, `ordered-steps`, `walkthrough`)
  — normally not comparable, because `rules/laconic.md` instructs the treatment arm to do
  exactly what the trap checks while the controls are not told. That asymmetry survives the
  relay in one direction only. A laconic *advantage* on these rows is still partly
  instruction-following and proves nothing. A laconic *deficit* would be real evidence,
  because no instruction can explain a treatment arm losing to an untold control. The rows
  are reported for that reason.
- **`rule-adherence`** (`conditional`, `decision`, `floor`) — criteria restated from
  laconic's own style prohibitions. Supports nothing in either direction, and is reported
  only so that no case is silently missing.
- **Never-cut token survival** — fully comparable in every arm. The parent is handed no
  rules at all, so what it can repeat is bounded by what its report kept.

`decision` in particular passed **zero** times in every arm, baseline included: the relay
prompt asks the parent to flag anything the report is missing, which pushes it toward
hedging, and `decision`'s trap fails on a hedge. That is a property of the relay prompt,
identical across arms, not an arm difference.

## Never-cut tokens survived the handoff in every arm

Five cases carry never-cut tokens. Failures are responses missing at least one:

| arm | subagent report (haiku · sonnet) | parent answer (haiku · sonnet) |
|---|--:|--:|
| via-baseline | 0/15 · 0/15 | 0/15 · 0/15 |
| via-lite | 0/15 · 0/15 | 0/15 · 0/15 |
| via-full | 0/15 · **1/15** | 0/15 · 0/15 |
| via-ultra | 0/15 · 0/15 | 0/15 · 0/15 |

One report in 120 lost a token, and the parent's answer got it back. That row deserves
naming rather than counting, because it is not laconic compression: on
`conditional`/sonnet/rep0 the subagent **edited `db.js` and replied "Applied."** in
eighteen words. `conditional` is one of the cases whose prompt lacks the "Don't edit
anything" clause that `evals/CRITERIA.md` documents, so the diagnosis went into the diff
instead of the report. The parent reconstructed "leak" by inference from "`idle` pinned at
0", and led with the fact that the report never said what had changed:

> It made some change to `db.js` ("Applied") but the report doesn't say *what* the fix was
> — I can't tell you which line or setting changed, so don't take my word for what's
> different in the code.

Read as a data point about relaying, that is mildly encouraging: a parent can sometimes
rebuild a dropped fact, and it does flag the gap. At n = 1 it is an anecdote, not a
finding.

## The compression the parent was actually exposed to

If the arms had handed the parent near-identical reports, a null result would mean
nothing. They did not:

| arm | haiku | sonnet |
|---|--:|--:|
| via-baseline | 108 | 175 |
| via-lite | 99 | 103 |
| via-full | 102 | 100 |
| via-ultra | 85 | 94 |

Median words per report, n = 33 per cell. On sonnet the laconic arms hand the parent
41–46% less text than baseline. On haiku the compression is weak — 6–21% — which is the
same adherence limit [2026-07-31-levels.md](2026-07-31-levels.md) found, and it means the
haiku columns above are a weaker test of the issue's worry than the sonnet columns. The
sonnet columns, where the compression is real, are also where the laconic arms tie or
lead.

## How good was the compression, and what it cost

The question the null result invites: if accuracy is unchanged, is the compression worth
keeping? On the subagent path specifically, the answer measured here is that the saving is
real in text and negative in money.

Output tokens the subagent spent generating its report, same subset, median:

| arm | haiku | sonnet |
|---|--:|--:|
| via-baseline | 750 | 1142 |
| via-lite | 748 (−0%) | 673 (−41%) |
| via-full | 768 (+2%) | 805 (−30%) |
| via-ultra | 690 (−8%) | 553 (−52%) |

Cost per subagent call, median USD:

| arm | haiku | sonnet |
|---|--:|--:|
| via-baseline | 0.01662 | 0.07145 |
| via-lite | 0.01859 (+12%) | 0.07546 (+6%) |
| via-full | 0.01916 (+15%) | 0.07596 (+6%) |
| via-ultra | 0.01923 (+16%) | 0.07758 (+9%) |

**Every laconic arm costs more per subagent call than no rules at all.** The token
breakdown shows why, and the effect is monotonic in slice size rather than noisy, so it is
not a sampling artifact between the two source snapshots:

| arm | haiku cache-creation | sonnet cache-creation |
|---|--:|--:|
| via-baseline | 4191 | 5528 |
| via-lite | 5223 | 6956 |
| via-full | 5422 | 7180 |
| via-ultra | 5552 | 7288 |

Injecting the rule slice adds roughly 1000, 1200 and 1300 cache-creation tokens at `lite`,
`full` and `ultra`, plus a matching bump in cache reads. On haiku, which barely compresses,
that input buys nothing. On sonnet the output saving is real but still smaller than the
input the slice costs. This reproduces the four-arm result already published in
[2026-07-31-benchmark.md](2026-07-31-benchmark.md) — laconic 0.0190 against baseline 0.0165
on haiku, 0.0767 against 0.0716 on sonnet — so it is a property of the plugin, not of this
run.

What the parent saves in context is correspondingly small. The report costs the parent
about 363 tokens at baseline and 227 at `full` on sonnet, so roughly **136 tokens saved per
subagent report**, or 189 at `ultra`; on haiku, 16 and 72. (Estimated at four characters per
token from the report text, which is the marginal cost of pasting the report into a parent
that is already running.)

Compression is also uneven across cases. Sonnet, baseline to `full`:

| case | change |
|---|--:|
| badnews | −54% |
| floor | −52% |
| silent-success | −51% |
| fail-open | −48% |
| conditional | −47% |
| stale-cache | −30% |
| decision | −25% |
| destructive | −21% |
| walkthrough | −5% |
| ordered-steps | +1% |
| code-fidelity | 0% |

The three that do not compress are the ones whose length the never-cut contract holds: a
four-step rotation procedure, a whole-flow walkthrough, and a command with every flag
explained. That is the rules working rather than failing, and it is the same shape of
result the never-cut table above reports.

## What this cannot answer

- **The three `quality` cases are diagnostic questions.** All three ask a model to find a
  bug in a small fixture. A subagent asked to enumerate a large surface — every call site,
  every config key — has more to lose to compression than one asked to name a root cause,
  and no case here is that shape.
- **One parent model.** Every relay was answered by sonnet. A weaker parent has less
  capacity to reconstruct, and the `conditional` anecdote above is exactly the behaviour
  that might not survive a downgrade.
- **The relay is not the live path.** A real subagent receives its task from a parent, runs
  under `SubagentStart`, and returns through the Task tool. Here stage one ran under
  `--append-system-prompt` against a user-style prompt, and stage two is a separate
  process. The rule text is identical; the framing is not.
- **`decision` never fired.** Zero passes in all four arms means that case contributed no
  signal about the handoff, only about the relay prompt.
- **n = 3 reps.** A real but small effect — five percentage points, say — would not be
  visible here. The result is "no detectable degradation", not "no degradation".
- **The cost figures are per call on this harness.** Each generation paid to establish its
  own cache. A live session amortises the rule slice across every subagent it spawns, so
  the per-call penalty above is an upper bound on the real one, and the compression saving
  is unaffected. The direction at n = 1 subagent per session is what the table shows; where
  it crosses over was not measured.
- **Three judge calls returned unparseable output** (`via-lite`/haiku: two `stale-cache`,
  one `decision`). They are excluded from every denominator and reported as `judge_failed`,
  which is why `via-lite`/haiku's quality row reads 7/7 rather than 9/9.

## Reproducing

```
python3 evals/bench/subagent.py generate --reps 3 --jobs 6
python3 evals/bench/judge.py --results evals/snapshots/subagent.json \
                             --out evals/snapshots/subagent-judgments.json
python3 evals/bench/subagent.py report --markdown /tmp/subagent-tables.md
```

snapshots or a different relay prompt. The tables below are what `report` emits.
